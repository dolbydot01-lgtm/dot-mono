## 参考答案

### A1

不可能三角指：在单层链上，同时最大化去中心化（普通节点可验证）、安全（抗攻击/抗重组）与可扩展（高吞吐）很困难。提高吞吐通常要求更高的带宽、存储与计算，普通节点被挤出，去中心化下降；若降低节点门槛，则吞吐受限。

Rollup 没有"打破"三角，而是**重新分配职能**：

- 执行：移到 L2，由排序器/证明系统完成。
- 结算：留在 L1，L1 合约裁决状态根。
- 共识：L2 有自己的排序共识（多数目前是单点），L1 提供最终结算。
- 数据可用性：批次数据放 L1 blob 或外部 DA，确保可重放。

新信任假设包括：排序器不会审查/停机（或有逃生通道）、证明系统可靠、DA 层真的保留数据、桥的验证者集合诚实、升级多签不被攻破。因此正确说法是：Rollup 用**新的工程信任假设**换取了 L1 层面的可扩展性。

### A2

| 维度 | Optimistic | ZK |
|---|---|---|
| 有效性 | 默认正确，挑战期内欺诈证明 | 每批附有效性证明 |
| 提款 | 挑战期结束（约 7 天） | 证明上链 + L1 最终性（分钟到小时） |
| L1 成本 | 数据 + 少量结算/挑战开销 | 数据 + 证明验证 gas + 证明生成 |
| 风险 | 观察者缺席、审查、升级多签 | 证明系统 bug、电路遗漏、可信设置 |

OP 的 7 天不是"交易要算 7 天"，而是给诚实观察者足够时间发现错误并提交欺诈证明。L2 内部的交易几秒内就被排序器接受；只有"安全提回 L1"需要等挑战期。

### A3

因素包括：

1. L1 重组与审查的持续时间：挑战交易必须能及时上链。
2. 观察者的监控成本与反应时间：需要有人持续运行节点、发现错误、准备保证金。
3. 攻击者的资金成本与 TVL：挑战期越长，攻击者占用资本越久，但用户提款成本也越高。
4. 升级/治理延迟：若升级可即时执行，挑战期毫无意义。
5. 跨链桥与做市商的流动性成本：7 天锁定资本的年化成本约为 `APR × 7/365`。

缩短到 1 天：资本成本降为 1/7，快速桥更便宜，用户体验更好；但观察者发现错误、组织保证金、在 L1 拥堵时上链的窗口也缩短，安全边际下降。Arbitrum 的 6.4 天是协议参数与区块时间共同作用的结果，不是必须等于 7×24 小时；"7 天"是行业惯例与安全经验的近似。

### A4

- Stage 0：有可运行的证明系统（欺诈证明或有效性证明），但升级由多签控制，安全委员会可快速干预，用户退出依赖运营方合作。
- Stage 1：证明系统实际运行且参与无需许可；合约升级有延迟；安全委员会有独立外部成员与较高阈值；用户有较强的退出保证。
- Stage 2：证明系统无需许可且覆盖全部状态；升级只能通过长延迟的链上治理；安全委员会仅在极窄的、预先定义的条件下可干预；用户无需运营方合作即可退出。

"有欺诈证明合约"只是 Stage 0 的必要条件之一。若证明提交有白名单、升级可即时多签执行、或数据不在 L1/可靠 DA 上，仍然不是 Stage 1。Stage 2 很少，因为它要求证明系统在工程上长期稳定、治理最小化、且所有状态转换都被覆盖；任何电路遗漏或治理后门都会使其降级。

### A5

- Type 1：与以太坊完全等价，包括共识层细节。复用全部工具链，但证明成本最高。
- Type 2：完全 EVM 等价，但不保证与 L1 共识完全一致。兼容绝大多数合约。
- Type 2.5：EVM 等价，但调整 gas 计量或少量系统合约，显著降低证明成本。
- Type 3：几乎 EVM 等价，缺少少数操作码/预编译，部分合约需改写。
- Type 4：只兼容高级语言（Solidity/Vyper），字节码不兼容，电路最简单、证明最快。

已有 DeFi 协议优先 Type 2 或 Type 2.5：它依赖 EVM 语义、预编译、gas 边界与既有审计假设；Type 3/4 可能需要改写合约并重新审计。若协议很简单、追求极致证明速度，且能接受改写，才考虑 Type 4。

### A6

只提交状态根不够，因为验证者需要交易数据来重放状态、发现欺诈或生成证明。如果数据被隐藏，排序器可以提交一个"看起来合法"的状态根，而无人能证明其错误；用户也无法独立构造退出证明。数据可用性是 Rollup 安全模型的前提，不是可选的存储优化。

- DAS：轻节点随机抽取数据块，若大部分数据缺失，抽样发现概率很高；全节点仍可重建。信任假设是抽样与网络层足够分散。
- PeerDAS：把 blob 切成列，验证者只 custody 部分列，用纠删码与抽样保证可用；降低单节点带宽，但增加列 custody 与网络拓扑的复杂性。
- 外部 DA：Celestia/EigenDA/Avail 等独立网络提供 DA。成本可能更低，但引入 DA 层验证者集合、桥、数据保留激励等新假设；若 DA 层停机或串谋，L2 可能无法出块或无法安全退出。

### A7

单一排序器可以决定交易顺序（MEV/抢跑）、延迟或审查交易、在宕机时停止出块，并可能选择性地打包。

- 共享排序：把多个 Rollup 的排序需求放入去中心化市场，排序者质押并受罚。限制单点审查，支持跨 Rollup 原子性；代价是跨域 MEV、治理与故障域扩大。
- Based rollup：把排序权交还 L1 proposer，继承 L1 的活性与抗审查；代价是出块节奏受 12 秒 slot 限制，预确认需要 proposer 承诺，MEV 流向 L1。
- 强制包含：用户可绕过排序器把交易提交到 L1，强制 L2 在期限内包含。保底抗审查；代价是延迟高、成本高，且需要 L1 合约的正确性。

三者可以组合：based 排序 + 强制包含 + 共享预确认。没有一种方案同时消除审查、延迟与 MEV 问题。

### A8

```
L2 收入 = 用户费用 − L1 数据成本
L2 利润 = L2 收入 − 排序器/证明/运营/激励成本
```

收入只扣除了最直接的 L1 数据成本；利润还要扣除执行、证明、人力、基础设施、代币激励、桥的流动性成本等。blob 费用很低时，L1 数据成本的主要部分是**提交批次的固定 gas**（calldata、验证、状态根更新），而不是 blob 本身；批次越大，固定成本被摊得越薄。

### B5

### C3

1. 每笔收入 `0.05 − 0.012 = $0.038`；月收入 `$38,000`；每笔利润 `0.038 − 0.005 − 0.003 = $0.030`；月利润 `$30,000`；利润率 `30,000 / 50,000 = 60%`（按用户费用计），或 `30,000 / 38,000 = 78.9%`（按收入计）。
2. 每笔收入 `0.05 − 0.036 = $0.014`；月收入 `$14,000`；每笔利润 `0.014 − 0.008 = $0.006`；月利润 `$6,000`；利润率 `6,000 / 50,000 = 12%`（按费用计），或 `6,000 / 14,000 = 42.9%`（按收入计）。
3. 用户费用 $0.02：每笔收入 `0.02 − 0.012 = $0.008`；月收入 `$8,000`；利润 `8,000 − 8,000 = $0`。用户费用 $0.015：每笔收入 `$0.003`；月收入 `$3,000`；利润 `3,000 − 8,000 = −$5,000`。
4. 对用户：费用下降是净福利，尤其是小额/高频交易。对排序器：若费用下降快于数据成本下降，利润被压缩，必须靠规模、MEV、排序市场或差异化服务。对代币持有人：若协议用代币补贴费用，代币增发会稀释持有人；若费用下降但交易量增长，净利润可能仍增长，但不能假设"更低费用 = 更高估值"。

### C4

没有唯一正确答案，评分看权衡是否完整。

- **单一排序器 + 强制包含**：100 ms 反馈容易实现（排序器先软确认），成本最低；但排序器可审查/抢跑，强制包含只能保底，延迟可能数分钟到数小时，不适合"防审查的实时操作"。适合大多数游戏，配合退出机制。
- **共享排序**：可获得跨游戏合约的原子排序与去中心化审查抵抗；代价是跨域 MEV、排序市场延迟（通常仍高于 100 ms）、治理与故障域扩大。适合多游戏/多 Rollup 的原子交互，但需要预确认机制。
- **Based rollup**：继承 L1 抗审查与活性，但出块受 12 秒 slot 限制；100 ms 反馈只能靠 L1 proposer 的预确认承诺，承诺失败时用户体验退化。适合把"结算安全"放在首位、能接受预确认信任的游戏。

一个合理设计是混合：游戏内高频操作在中心化 sequencer/游戏服务器上做软确认，定期把状态根与 DA 提交到 based rollup 或 L1；提供强制包含与退出通道；跨游戏原子操作走共享排序或消息协议。关键是明确"哪些操作需要即时最终性、哪些可以延迟结算"，而不是盲目追求单一技术标签。
