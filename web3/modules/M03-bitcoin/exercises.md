## 参考答案

**A1**　UTXO 集是
$$
U=\{(txid,vout)\mapsto(value,scriptPubKey)\}.
$$
交易声明一组输入 outpoint，每个 outpoint 必须存在于 $U$ 且未被花费；交易产生新的输出，加入 $U$。合法性要求输入总额等于输出总额加手续费：
$$
\sum value(in)=\sum value(out)+fee.
$$
链上没有“Alice 的余额”字段；钱包余额是它控制的所有 UTXO 之和。UTXO 模型的优点是并行验证、无全局 nonce、隐私边界清晰；缺点是没有账户抽象、找零与币选择复杂、状态是输出集合。账户模型的优点是直观、易支持智能合约；缺点是需要 nonce、全局状态读写与重放保护。手续费不是独立输出，而是输入减输出的差额，由矿工在 coinbase 中领取。

**A2**　P2PKH：
```
scriptPubKey: OP_DUP OP_HASH160 <20 字节 pubkey hash> OP_EQUALVERIFY OP_CHECKSIG
scriptSig:    <signature> <public key>
```
栈过程：初始 `[sig,pub]`；`DUP` → `[sig,pub,pub]`；`HASH160` → `[sig,pub,H(pub)]`；压入锁定脚本中的 hash → `[sig,pub,H(pub),hash]`；`EQUALVERIFY` 比较并删除 → `[sig,pub]`；`CHECKSIG` 验证签名 → `[true]`。P2SH 把复杂赎回脚本的哈希放进 `scriptPubKey`（`OP_HASH160 <hash> OP_EQUAL`），发送方只需付固定长度地址，收款方在花费时提供赎回脚本；验证器先检查哈希，再执行赎回脚本。2-of-3 多签赎回脚本：
```
OP_2 <pub1> <pub2> <pub3> OP_3 OP_CHECKMULTISIG
```
任意两个签名即可通过。`OP_CHECKMULTISIG` 有历史 off-by-one，需要额外压入一个占位元素（通常是 `OP_0`）。

**A3**　CLTV 检查交易的绝对 `locktime`（区块高度或 Unix 时间）是否达到脚本指定的值；CSV 检查输入的相对年龄（由 `sequence` 编码的块数或时间）是否达到脚本指定的值。两者都要求输入的 `sequence` 不是 `0xffffffff`（final），否则时间锁不生效。CLTV 适合“到某个高度后才能取”的遗产/托管；CSV 适合支付通道的“相对撤销窗口”、状态通道与 vault。CLTV 是绝对时间，CSV 是相对时间；前者看交易的 locktime，后者看输入的 sequence。

**A4**　交易延展性是指攻击者可以在不改变交易效果的情况下修改签名字节（如 ECDSA DER 重编码、high-S），从而改变 txid。依赖未确认 txid 的协议（支付通道、退款、惩罚交易）会因此失效。SegWit 把 witness（签名）移出 txid 的承诺范围：`txid` 只对 stripped 交易做双 SHA-256，`wtxid` 对含 witness 的完整交易做双 SHA-256；签名重编码只会改变 wtxid，不改变 txid（但会改变 wtxid，P2P 层需处理）。weight 计算：
$$
weight=4\times|stripped|+|witness|,\qquad vsize=\lceil weight/4\rceil.
$$
非 SegWit 交易的 weight 是字节数的 4 倍；SegWit 的 witness 字节按 1 倍计，因此享受折扣。

**A5**　Schnorr 签名支持原生聚合（MuSig2），让多签在链上看起来像单签，签名更短、验证更简单；MAST 把脚本的多个分支做成 Merkle 树，花费时只揭示执行的分支，未执行分支只留哈希，提升隐私、降低 witness 大小；key path / script path 让输出可以先用聚合公钥直接签名（key path），需要复杂条件时才揭示脚本分支（script path）。Taproot 没有取消 Script：它仍然执行脚本，只是改变了承诺方式与花费路径；普通支付与复杂合约在链上可以难以区分。

**A6**　每 210,000 个区块，补贴减半：50、25、12.5、6.25、3.125、1.5625…… 总供给是各 epoch 发行量之和。忽略整数截断时是几何级数：
$$
210000\times50\times\sum_{i=0}^{\infty}2^{-i}=21{,}000{,}000.
$$
但每个 epoch 都向下取整到整数 satoshi，实际为 20,999,999.9769 BTC，少 0.0231 BTC；第 32 个 epoch 只剩 1 sat，之后为 0。减半由区块高度触发，不是日历事件；按 10 分钟/块，210,000 块约 3.995 年，实际日期会随算力与出块速度漂移，所以“每 4 年”只是近似。

**A7**　HTLC 同时锁定哈希与时间：谁揭示 $H$ 的原像谁就能取走资金，到期未揭示则退款。路径上每一跳使用同一个 $H$，但时间锁逐跳递减（$T_1>T_2>\dots$）。最终收款人揭示原像后，原像沿路径反向传播，每一跳都能在各自到期前领取；如果失败，时间锁从最靠近收款人的一跳开始依次退款。原子性来自“同一个原像”与“递减的超时”：中间节点不能在没有拿到上游资金的情况下安全地支付下游，也不能卷款跑路。若中间节点在关键时刻离线，它可能错过领取窗口而损失资金；watchtower、足够的 $T_1-T_2$ 缓冲与重试机制可以缓解。$T_1-T_2$ 太小则没有足够时间广播领取交易，尤其在手手续费飙升或链拥堵时。

**A8**　Ordinals/Inscriptions 把数据写入 Taproot witness，数据可用性由比特币链提供，但索引与“铭文”语义是社会约定，不是共识层资产；BRC-20/Runes 的信任取决于索引器与社区共识。Bitcoin L2 的信任模型差异很大：Lightning 依赖通道与惩罚机制；Stacks/Rootstock 等项目依赖锚定、联邦或联合签名；BitVM 依赖挑战期与诚实观察者；Babylon 的 BTC 质押依赖比特币时间戳、脚本与外部 PoS 的罚没逻辑。它们都在不同程度上复用比特币的安全性，但不是“和比特币共识完全等价”。BTC 质押不是比特币原生的 PoS；把币锁在脚本里不等于把比特币共识安全租给另一条链。

**C3**　参考要点：2010 年 8 月，区块 74638 中的一笔交易利用整数溢出，产生两个各约 922 亿 BTC 的输出，总计约 1840 亿 BTC。原因是当时对交易输出金额求和的检查存在有符号 64 位整数溢出：攻击者构造使总和溢出的输出，绕过了“金额在范围内”的检查。社区迅速发布修复版本，并通过重组/孤立该区块清除异常交易；这些币从未被接受为合法 UTXO。教训：共识代码必须对所有算术做溢出检查（后来使用 `MoneyRange`、`CheckTransaction` 等），必须有边界测试与快速响应机制；共识错误可能导致“凭空造币”，但修复依赖矿工、开发者与用户的协调。SegWit（2017）与 Taproot（2021）都是**软分叉**：旧节点不识别新规则，但新交易/区块在旧节点看来仍然合法（例如 SegWit 输出对旧节点是 anyone-can-spend，Taproot 输出是 v1 witness 的未知类型），因此不会立即分裂网络。激活过程涉及 BIP9、矿工信号、用户激活讨论与社区共识，说明比特币治理不是单一主体决策，而是“rough consensus + 运行代码”。

**C4**　参考方案：地址类型优先 P2WPKH/P2TR（费用低、Taproot 隐私与聚合签名）；热钱包与冷钱包分离，冷钱包多签/HSM。UTXO 管理：按金额与确认数选择币，避免大量粉尘 UTXO；定期合并（consolidation）但避开高费期；找零地址使用新地址，避免地址复用。手续费：用 mempool 费率估算，支持 RBF/CPFP；提现批量处理，设置费率上限与重试。确认数：按金额分层（小额 1–3、中大额 6+、大额等待更多确认或人工审核），并监控重组深度。重组监控：跟踪 tip、finality/确认数、异常孤块；暂停充值/提现的阈值与应急预案。闪电网络适合小额、高频提现，但需评估通道流动性、在线率与托管风险。关键风险：手续费飙升、UTXO 粉尘、地址复用隐私、重组、内部密钥管理、合规与制裁筛查。

**D1**　参考角度：① 手续费需求取决于 L1 区块空间需求；L2/批处理可能降低需求，但也可能把结算与争议锚定回 L1。② 币价上升会提高美元计价的攻击成本，但也提高安全预算的美元值；市值与安全预算的比例是更好的指标。③ 攻击成本不仅是算力/质押，还包括被罚没、司法追索、交易所 KYC 与声誉。④ 矿工集中度、矿池可切换性、能源地缘政治会影响实际安全。⑤ 需要监测：手续费占矿工收入比例、区块空间利用率、平均费率、L2 结算频率、算力/矿池集中度、安全预算/市值比、重组深度与最终性延迟。
