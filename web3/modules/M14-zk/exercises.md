## 参考答案

### A1

- 完备性：若陈述为真且证明者诚实，验证者以压倒性概率接受。
- 可靠性：若陈述为假，任何多项式时间证明者让验证者接受的概率可忽略。
- 零知识性：存在多项式时间模拟器，在没有 witness 的情况下生成与真实交互不可区分的 transcript。

"证明"通常指信息论/统计可靠性（即使无限算力也不能作弊）；"论证"只保证计算可靠性（多项式时间作弊者无法成功）。SNARK 的 "A" 是 argument：它依赖计算假设（如离散对数、配对），因此严格来说是论证，不是信息论证明。

### A2

协议：

```
1. P 选 k ← Z_n，R = kG，发送 R
2. V 选 c ← Z_n，发送 c
3. P 计算 z = k + c·x mod n，发送 z
4. V 检查 zG == R + cP
```

验证：

```
zG = (k + c·x)G = kG + c(xG) = R + cP
```

模拟器：选随机 `c, z`，令 `R = zG − cP`，输出 `(R, c, z)`。验证方程成立：

```
zG = (zG − cP) + cP = R + cP
```

在真实协议中，`c` 由验证者随机选择，模拟器不能控制它；在随机预言机模型里，模拟器可以编程哈希得到想要的 `c`，所以 transcript 不可区分。

nonce 重用：同一 `k` 下得到 `z1 = k + c1x`、`z2 = k + c2x`，相减得 `z1−z2 = (c1−c2)x`，因此 `x = (z1−z2)/(c1−c2) mod n`。这也说明随机数必须新鲜，或使用 RFC 6979 的确定性 nonce。

### A3

挑战应绑定：

```
c = H(domain_separator || public_key || statement/message || R)
```

如果只算 `c = H(R)`：

- 证明/签名不绑定消息。攻击者可以把一个有效签名 `(R,z)` 原样附在另一条消息上；验证者重新计算 `c=H(R)`，仍得到相同挑战，于是接受。签名 scheme 因此可延展/可重放。
- 不绑定公钥：同一 transcript 可能在不同密钥/身份之间被误用（取决于验证方程，通常还需要其他条件，但至少缺少身份绑定）。
- 不绑定 domain/chainId/合约地址：跨链或跨应用重放。

具体场景：一个 zk 认证合约用 `c=H(R)` 验证"用户知道私钥"，但不把 `msg.sender`、chainId、action 放进去。攻击者截获一次登录证明，就能在另一条链或另一个 action 上重放，冒充用户。修复：使用 Strong Fiat–Shamir，把所有上下文纳入哈希，并做 domain separation。

### A4

R1CS 约束：

```
⟨a_i, w⟩ · ⟨b_i, w⟩ = ⟨c_i, w⟩
```

其中 `w` 是变量向量（含常数 1），`a_i, b_i, c_i` 是系数向量。每条约束只允许一次乘法。

QAP：对每个变量位置，插值出 `A(x), B(x), C(x)`，使得在约束点 `x=i` 上，`⟨A(i), w⟩` 等等于第 `i` 条约束的系数组合。令 `Z(x)=∏(x−i)`。若所有约束满足，则 `A(x)B(x)−C(x)` 在每个 `i` 处为零，因此被 `Z(x)` 整除，存在商 `H(x)`。反之，若整除，则在每个 `i` 处为零，约束满足。

只检查一个随机点不够，因为证明者可以在看到 `r` 后临时定义 `H(r)` 来满足等式（Lab 14.2 展示了 `r=3` 时取 80、`r=5` 时取 47 的"自适应"作弊）。必须让证明者先通过多项式承诺固定 `A, B, C, H`，再用随机点检查；承诺的绑定性阻止事后更改。

### A5

| 维度 | KZG | FRI |
|---|---|---|
| 可信设置 | 需要 powers-of-tau ceremony | 不需要 |
| 证明大小 | 常数（约一个群元素） | 对数级，较大 |
| 验证成本 | 低（配对） | 较高（哈希/Merkle 路径） |
| 假设 | 配对群上的 q-SDH/离散对数 | 抗碰撞哈希 + 低度测试 |
| 抗量子 | 否 | 是（哈希假设下） |

zkEVM 常用 KZG/PLONK：L1 验证 gas 贵，常数大小证明与低验证成本更重要；可信设置可以通过多参与者 ceremony 管理。zkVM/STARK 常用 FRI：需要透明设置、通用计算、抗量子，且证明通常不在 L1 上逐个验证（或能接受更大证明/聚合）。

### A6

| 维度 | SNARK | STARK |
|---|---|---|
| 证明大小 | 几百字节 | 几十到几百 KB |
| 验证 | 快，gas 低 | 较慢，gas 较高 |
| 可信设置 | 常见 | 不需要 |
| 假设 | 配对/离散对数 | 哈希/Fiat–Shamir |
| 抗量子 | 否 | 是（哈希假设下） |

SNARK 不一定是零知识的：它可能只证明计算正确，witness 在 transcript 中泄露。STARK 也不等于"完全无信任"：它信任哈希函数、实现、参数选择与 Fiat–Shamir 启发式；代码 bug 仍可破坏可靠性。

### A7

zkVM：把通用指令集（如 RISC-V）编译成电路，证明"程序在输入上执行得到输出"。开发者写普通程序，通用性好；但每条指令都要约束，开销大。

zkEVM：专门为 EVM 语义/字节码设计电路，兼容 Solidity 工具链；兼容性越强（Type 1/2），电路越复杂、证明越慢。

递归证明：一个证明验证另一个证明，形成证明链/树，使证明大小不随计算量线性增长，适合长计算与跨链证明。证明聚合：把多个证明压缩成一个，降低链上验证次数。二者都不免费：递归/聚合增加证明生成时间、内存与实现复杂度，聚合证明本身的生成也有成本；只有在批次足够大、验证 gas 足够贵时才划算。

### A8

1. **Tornado**：固定面额存款，`leaf=Poseidon(secret,nullifier)` 插入 Merkle 树；提款时证明叶子在树中，公开 `nullifierHash` 防双花，relayer 代付 gas。信任边界：合约/电路正确、匿名集足够大、relayer 不记录 IP、用户不泄露时间/金额关联。
2. **zk 身份**：发行者签名 credential；用户证明"credential 有效 ∧ 谓词成立 ∧ nullifier=H(secret,scope)"。信任边界：发行者可信、撤销机制有效、scope 设计合理、证明系统不泄露属性。
3. **zkRollup**：排序器执行批次，生成状态转移证明，L1 验证；数据必须可用。信任边界：证明系统/电路正确、DA 层可靠、桥/合约正确、排序器不审查（或有逃生通道）。
4. **coprocessor**：链下索引链上数据并计算，生成"输入承诺 + 程序执行"的证明，链上验证。信任边界：输入数据可用且承诺正确、程序/电路正确、coprocessor 不选择性隐藏数据。

```

a1 = [0,1,0,0,0]
b1 = [0,1,0,0,0]
```

```
A(1)=3, A(2)=13 → A(x)=10x+94
B(1)=3, B(2)=1  → B(x)=99x+5
C(1)=9, C(2)=13 → C(x)=4x+5
Z(x)=(x−1)(x−2)=x²+98x+2
```

检查：`A(1)=104≡3`，`A(2)=114≡13`；`B(1)=104≡3`，`B(2)=203≡1`；`C(1)=9`，`C(2)=13`。

3. `A·B−C` 在 `x=1,2` 为零，且次数为 2，`Z` 也是 2 次，所以 `H` 是常数。代入 `x=1` 或 `x=2` 的一组值可解得 `H=81`。在 `r=5`：

```
A=10·5+94=144≡43
B=99·5+5=500≡96
C=4·5+5=25
Z=25+490+2=517≡12
A·B−C=43·96−25=4103≡63
H·Z=81·12=972≡63 ✓
```

```
A·B−C'=43·96−29=4099≡59
H·Z=63
59≠63，拒绝
```

5. 错误多项式 `A·B−C'−H·Z` 的次数为 2，域大小 101，随机点命中根的概率 `≤2/101 = 1.980198%`。

### C3

1. 公开输入：`root`（存款 Merkle 根）。私有输入：`secret`、`nullifier`、`pathElements[depth]`、`pathIndices[depth]`。公开输出：`nullifierHash`。对应 Tornado：root 是当前存款树根，secret/nullifier 是存款时生成的秘密，path 是成员路径，nullifierHash 用于防双花。
2. 约束 `pathIndices` 只能是 0 或 1，保证左右选择合法。如果删掉，证明者可以取 `pathIndices=2` 等值，使 `left/right` 的线性组合跳出二叉树结构，可能构造出不在树中的路径或绕过根检查。这是"约束不足"的典型例子。
3. Poseidon 是专门为 zk 电路设计的哈希，在有限域上约束数远少于 Keccak-256（Keccak 的位运算在算术电路里非常昂贵）。用 Poseidon 能显著减少 R1CS 约束与证明时间；代价是它不是以太坊原生的哈希，链上验证/其他合约要用对应实现，且必须确认其参数与安全版本。
4. `2^20 = 1,048,576` 个叶子。超过后需要更深的树或新树；旧树中的存款仍可提款，但新存款进入新树，协议要维护多棵树/根的历史，并确保提款时根在允许集合中。
5. 没有证明：存款金额（电路不绑定面额）、存款时间、提款地址与存款地址的关系、relayer 身份、用户是否被胁迫、资金是否来自合法来源、树的根是否是最新的。协议层还需要：固定面额、root 历史管理、nullifier 集合、relayer 激励、合规筛查、前端/合约的升级治理、以及可信设置/电路审计。

### C4

一个可行设计：

1. **承诺**：对每个合格地址 `addr_i`，生成 `leaf_i = H(addr_i || salt_i)`；构建 Merkle 树，链上公布 `root`。也可以把 `salt_i` 通过私密渠道发给用户。
2. **witness 与公开输入**：私有 witness = `addr_i, salt_i, pathElements, pathIndices`；公开输入 = `root, airdropId, recipient`；nullifier = `H(addr_i || airdropId)`（或 `H(secret_i || airdropId)`）。电路证明：叶子在树中 ∧ nullifier 计算正确 ∧ recipient 是调用者指定/签名的地址。
3. **防重复**：链上维护 `usedNullifiers` 集合；同一 nullifier 第二次领取 revert。**防 front-running**：nullifier 公开后，攻击者可能抢先用它领取；让电路公开 `recipient`，并在合约里要求 `msg.sender == recipient`，或让用户对 `(nullifier, recipient, deadline)` 签名；relayer 只能代付 gas，不能改收款人。**防 relayer 盗领**：收款地址由用户签名/指定，relayer 只收固定费用。
4. **信任假设**：合格集合构造正确（没有漏掉/多算地址）；Merkle 树/电路实现正确；可信设置（若用 Groth16）安全；空投合约不可升级或升级有延迟；用户保管好 salt/secret。**隐私泄露**：领取时间、gas 支付方式、recipient 与合格地址的链上关联、金额（如果空投量按地址分层）、relayer 的 IP/日志；匿名集是"尚未领取的合格地址"，越晚领取匿名集越小。
5. **可追溯设计**：引入可信第三方持有的 viewing key，或把 `addr_i` 用监管公钥加密后附在承诺中；必要时通过门限解密/法院命令追溯。代价是：不再对监管者匿名、viewing key 持有者成为信任/攻击中心、用户可能因"可追溯"而降低使用意愿；需要明确披露与最小化保留。替代方案是"证明清白"（association set/制裁筛查）而不是完全追溯，折中隐私与合规。
