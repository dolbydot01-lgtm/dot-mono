# 智能合约审计报告模板

> 用法：复制本文件到 `capstone/docs/audit-report.md`，按实际项目填写。删除不适用的章节，但不要删除"范围与限制""发现分级""残余风险"三节。本模板借鉴公开审计报告（Trail of Bits、OpenZeppelin、Spearbit）的常见结构，不是任何机构的官方格式。

## 0. 元信息

| 字段 | 内容 |
|---|---|
| 项目 / commit | 仓库 URL + commit hash |
| 审计范围 | 合约文件、部署脚本、权限配置 |
| 版本 / 日期 | vX.Y · YYYY-MM-DD |
| 审计人 | 姓名 / 团队 |
| 审计类型 | 人工审查 + 工具 + 测试（说明哪些） |

## 1. 执行摘要（Executive Summary）

- 一段话说明系统做什么、审计了什么、总体结论；
- 发现数量按严重级别统计；
- 最关键的 1–3 个风险；
- 明确说明：**审计不是安全保证**，只覆盖特定 commit 与特定假设。

## 2. 范围与限制（Scope & Limitations）

**在范围内**

- 文件列表 + 每个文件的职责；
- 部署参数与管理员权限；
- 依赖的外部合约 / 预言机 / 代币行为假设。

**不在范围内**

- 前端、后端、密钥管理、链下基础设施（如有，单独说明）；
- 未列出的分支、未部署的合约、未来升级；
- 经济参数是否合理（除非明确纳入）。

**限制**

- 时间、测试覆盖率、无法复现的环境；
- 依赖的信任假设（如"管理员诚实""预言机不会同时失效"）。

## 3. 系统概述（System Overview）

- 架构图（合约调用关系、资产流向）；
- 核心不变量（invariants），例如：
  - `totalSupply == Σ balances`
  - 池中资产价值 ≥ 债务价值 × 清算阈值
  - 只有 owner 能调用 `setFee`
- 角色与权限表：owner / admin / guardian / keeper / user；
- 关键状态机（存款 → 借款 → 清算 → 还款）。

## 4. 威胁模型（Threat Model）

| 攻击者 | 能力 | 目标 |
|---|---|---|
| 普通用户 | 任意调用公开函数、闪电贷、MEV | 窃取资金、操纵价格、阻塞他人 |
| 管理员 | 升级、改参数、暂停 | 作恶或密钥泄露 |
| 外部协议 | 预言机失真、代币回调、重入 | 清算错误、坏账 |
| 跨链 / 桥 | 消息伪造、重放 | 双重铸造、资金盗取 |

列出**信任边界**：哪些输入来自不可信方？哪些调用会转移控制权（`call`、`delegatecall`、ERC-777 hook）？

## 5. 发现分级（Severity）

| 级别 | 定义 | 例子 |
|---|---|---|
| Critical | 可直接导致资金损失 / 永久冻结，且无需特殊条件 | 任意人可提取全部资金 |
| High | 可导致重大损失，但需要特定条件 | 预言机操纵后清算错误 |
| Medium | 业务逻辑错误、可用性受损、有限损失 | 费率计算错误、DoS |
| Low | 最佳实践、边界条件、Gas | 缺少事件、零地址检查 |
| Informational | 代码质量、文档、命名 | 注释错误 |

## 6. 发现列表（Findings）

每条发现使用统一格式：

```markdown
### [H-01] 清算函数可被重入，重复扣减抵押品

- **严重级别**：High
- **位置**：`LendingPool.sol:142`（commit abc123）
- **状态**：已修复 / 已确认 / 未修复 / 风险接受

**描述**
调用 `liquidate()` 时先向清算人转出抵押品，后更新 `debt` 状态；抵押品若为 ERC-777 代币，转账会触发 `tokensToSend` 回调，攻击者可在状态更新前再次进入 `liquidate()`。

**影响**
同一笔债务被多次清算，清算人重复获得抵押品，池子出现坏账。攻击成本仅为 gas + 闪电贷手续费。

**复现（PoC）**
```solidity
function testLiquidateReentrancy() public {
    // 1. 部署恶意 ERC-777 抵押品
    // 2. 开仓并压低价格
    // 3. 调用 liquidate，回调中再次 liquidate
    // 4. 断言清算人获得的抵押品 > 债务
}
```

**建议**
遵循 checks-effects-interactions：先更新 `debt` 与 `collateral`，再转账；或使用 `nonReentrant`；或采用 pull-payment。

**修复验证**
修复 commit `def456`；回归测试 `testLiquidateReentrancy` 通过；Slither 无相关告警。
```

建议按严重级别排序，编号 `C-01`、`H-01`、`M-01`、`L-01`、`I-01`。

## 7. 工具与测试

| 工具 / 方法 | 配置 | 结果 |
|---|---|---|
| Slither | `slither . --config-file` | 0 critical/high；列出未处理告警 |
| Foundry test | `forge test -vvv` | X tests passed |
| Foundry fuzz | `forge test --fuzz-runs 10000` | 覆盖函数与不变量 |
| Invariant test | `invariant_*` | 不变量在 N 次调用后仍成立 |
| 主网分叉 | `--fork-url` + 区块号 | 与真实协议交互 |
| 人工审查 | 逐行 + 调用图 | 发现列表 |

**覆盖率**：说明工具、行覆盖率与分支覆盖率；覆盖率不是安全性的证明。

## 8. 残余风险（Residual Risk）

即使所有发现修复，仍存在的风险：

- 管理员多签 / 升级密钥被攻破；
- 预言机极端行情下失真；
- 依赖的稳定币脱锚；
- 治理攻击；
- 未知漏洞与实现错误。

对每项给出**可能性 × 影响**与缓解措施（时间锁、限额、暂停开关、保险、监控）。

## 9. 建议与优先级

- P0：上线前必须修复；
- P1：上线后 30 天内修复；
- P2：下个版本；
- P3：文档 / 代码质量。

## 10. 附录

- 完整文件哈希 / commit；
- 测试命令与输出摘要；
- 术语表；
- 与项目方的沟通记录（可选）。
